## 1. Executive Summary

Shorebreak is Lil Dude's on-device wave generator — it detects capability gaps,
generates code, security-scans it, sandboxes it, and (with owner approval) installs
it locally. Today, that cycle is entirely private: the generated wave lives on one
machine. **The Community Wave Hub extends Shorebreak outward** so that any Lil Dude
user can package a wave (hand-built or Shorebreak-generated), publish it to a shared
registry, and let others discover, review, and install it — all while preserving the
project's foundational principles: **Security > Cost > Performance > Approachability**.

### What "Shorebreak Community Hub" Is NOT

- It is **not** a hosted SaaS marketplace (no Lil Dude cloud accounts).
- It is **not** a centralized binary distribution system.
- It is **not** a way to bypass the existing security scanner or sandbox.

### What It IS

- A **GitHub-native publishing pipeline** backed by the existing
  `lildude-community/wave-registry` repo.
- A **CLI publish command** (`lil-dude publish`) that packages, validates, and
  submits waves via GitHub PR.
- A **CI validation pipeline** (GitHub Actions) that runs the security scanner,
  sandbox tests, and manifest checks on every submission.
- **Enhanced discovery UI** in the Skills Hub with community profiles, verified
  badges, changelogs, and dependency metadata.
- **Trust-tiered installation** — published waves carry a `communityTrust` score
  derived from scan results, review count, install count, and author history.

## 2. Architecture Decision: Where Does It Live?

### Options Evaluated

| Option | Pros | Cons |
|--------|------|------|
| **A. New repo (`lildude-community/shorebreak`)** | Clean separation; community can fork/manage independently | Extra CI/CD; version drift between main repo and community tooling |
| **B. Subtree in this repo** | Single build; shared types/scanner; atomic PRs | Bloats main repo; harder for community contributors |
| **C. Hybrid: CLI + validation in main repo, registry stays separate** | Best of both — tooling ships with Lil Dude, registry is community-owned | Requires coordinated releases |

### Decision: **Option C — Hybrid**

**Rationale (by principle):**

1. **Security:** The security scanner, sandbox runner, and manifest validator
   already live in `src/waves/`. Keeping the publish CLI in the same repo means
   publish-time validation uses the *exact same code* as install-time validation.
   No version skew, no duplicated security logic.

2. **Cost:** No separate build system or CI matrix. The GitHub Actions workflow
   for the registry repo is lightweight (calls the scanner as a package).

3. **Performance:** The CLI ships as part of `dist/cli.js` — zero extra
   install for users.

4. **Approachability:** `lil-dude publish` is one command. No separate toolchain.

### Repo Responsibilities

| Repo | Owns |
|------|------|
| **`lildude` (this repo)** | `lil-dude publish` CLI, `src/waves/packager.ts`, `src/waves/publisher.ts`, enhanced hub API, Skills Hub UI updates, trust scoring |
| **`lildude-community/wave-registry`** | `registry.json` (v3 format), individual wave packages (`waves/{name}/`), GitHub Actions CI, `CONTRIBUTING.md`, moderation policy |

## 3. Registry Format v3

The current registry is a single `registry.json` with v1/v2 backward compat
(`parseRegistryPayload` in `hub-registry.ts`). v3 extends this for community
publishing.

### 3.1 Directory Structure (wave-registry repo)

```
wave-registry/
  registry.json               ← master index (auto-generated by CI)
  categories.json             ← category definitions
  CONTRIBUTING.md              ← submission guide
  .github/
    workflows/
      validate-submission.yml  ← PR validation pipeline
      rebuild-registry.yml     ← regenerate registry.json on merge
  waves/
    weather-checker/
      wave.json                ← manifest
      index.js                 ← entry point
      README.md                ← optional docs
      CHANGELOG.md             ← version history
      .scan-result.json        ← CI-generated scan output
    email-summarizer/
      ...
```

### 3.2 registry.json v3 Schema

```typescript
interface RegistryV3 {
  version: '3.0.0';
  generatedAt: string;                   // ISO timestamp
  categories: CategoryDefinition[];
  featured: string[];                     // wave names
  waves: WaveRegistryEntryV3[];
}

interface WaveRegistryEntryV3 extends WaveRegistryEntry {
  // New v3 fields (all optional for backward compat)
  publishedAt?: string;                   // first publish date
  updatedAt?: string;                     // last update date
  packageHash?: string;                   // SHA-256 of wave package
  scanPassed?: boolean;                   // CI scan result
  sandboxPassed?: boolean;                // CI sandbox result
  communityTrust?: number;                // 0–100 computed score
  dependencies?: string[];                // other wave names
  minLilDudeVersion?: string;             // semver compat
  repositoryUrl?: string;                 // source repo link
  license?: string;                       // SPDX identifier
  screenshots?: string[];                 // relative paths to images
}
```

### 3.3 Backward Compatibility

`parseRegistryPayload` already handles v1 and v2. v3 extends v2 — all new fields
are optional. The existing `fetchRegistry()` 3-layer cache works unchanged:

```
In-memory (5s) → SQLite wave_hub_cache (24h) → Remote fetch (ETag) → Fallback
```

### 4.2 CLI Command: `lil-dude publish`

**New file:** `src/cli/commands/publish.ts`

```
Usage: lil-dude publish <path> [options]

Arguments:
  path              Path to wave directory (must contain wave.json + index.js)

Options:
  --dry-run         Validate and scan without opening a PR
  --skip-sandbox    Skip sandbox execution (scan still required)
  --registry-repo   Override registry repo (default: lildude-community/wave-registry)
  --github-token    GitHub PAT for PR creation (or set GITHUB_TOKEN env var)
```

**Validation steps (in order):**

1. **Manifest validation** — Parse `wave.json` against `WaveManifestSchema` (Zod).
   Fail if missing required fields or invalid values.

2. **Naming rules** — `name` must be kebab-case, 3–50 chars, alphanumeric + hyphens.
   Must not conflict with bundled wave names. Must not start with `lil-dude-` prefix
   (reserved for official waves).

3. **Security scan** — Run `scanWaveCode()` on `index.js`. Fail on any critical
   finding. Warn on high findings. Medium/low are informational.

4. **Sandbox test** — Run `executeSandboxed()` with mock parameters. Must not crash
   or timeout. Captures output for review.

5. **Package integrity** — Compute SHA-256 hash of all wave files. Store in
   `.scan-result.json` alongside the wave.

6. **Size check** — Total package must be under 100KB (prevents binary blobs).

7. **Confirmation prompt** — Show scan summary, size, and ask user to confirm.

8. **PR creation** — Fork registry repo, create branch `wave/{name}-{version}`,
   copy files, open PR with structured body.

## 5. CI Validation Pipeline (wave-registry repo)

### 5.1 `validate-submission.yml`

Runs on every PR to `main` that touches `waves/*/`.

```yaml
name: Validate Wave Submission
on:
  pull_request:
    paths: ['waves/**']

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }

      # Install lil-dude as a dev dependency (for scanner + sandbox)
      - run: npm install lildude@latest

      # Detect which waves were added/modified
      - id: changed
        run: |
          WAVES=$(git diff --name-only origin/main -- waves/ | cut -d/ -f2 | sort -u)
          echo "waves=$WAVES" >> $GITHUB_OUTPUT

      # Validate each changed wave
      - name: Validate waves
        run: |
          for WAVE in ${{ steps.changed.outputs.waves }}; do
            npx lil-dude validate-wave "waves/$WAVE"
          done

      # Post results as PR comment
      - name: Post results
        uses: actions/github-script@v7
        with:
          script: |
            // Read validation output and post as PR comment
```

### 5.2 `rebuild-registry.yml`

Runs on push to `main` (after PR merge). Scans all `waves/*/wave.json` files,
computes aggregate data, and writes `registry.json` v3.

```yaml
name: Rebuild Registry
on:
  push:
    branches: [main]
    paths: ['waves/**']

jobs:
  rebuild:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: node scripts/build-registry.js
      - run: |
          git config user.name "shorebreak-bot"
          git config user.email "bot@lildude.dev"
          git add registry.json
          git commit -m "chore: rebuild registry" || true
          git push
```

### 5.3 `validate-wave` CLI Subcommand

**New file:** `src/cli/commands/validate-wave.ts`

```
Usage: lil-dude validate-wave <path>

Validates a wave directory against community submission standards.
Exits with code 0 on pass, 1 on fail. Output is structured JSON.
```

This is the same validation logic used by `lil-dude publish` but designed to run
headless in CI. Outputs structured JSON for GitHub Actions to parse and comment.

## 6. Community Trust Scoring

### 6.1 Trust Score Model

Every published wave receives a `communityTrust` score (0–100) computed from:

| Factor | Weight | Scoring |
|--------|--------|---------|
| Security scan | 30 | 30 if clean, -10 per high finding, -30 per critical |
| Sandbox pass | 15 | 15 if passed, 0 if skipped/failed |
| Review count | 15 | min(reviewCount, 10) * 1.5 |
| Average rating | 15 | (averageRating / 5) * 15 |
| Install count | 10 | min(log10(installCount + 1) * 5, 10) |
| Author history | 10 | min(authorPublishedCount * 2, 10) |
| Age (days published) | 5 | min(daysSincePublish / 30, 5) |

### 6.2 Trust Tiers

| Score | Tier | UI Treatment |
|-------|------|-------------|
| 80–100 | Trusted | Green badge, no warning on install |
| 50–79 | Community | Blue badge, brief disclaimer on install |
| 20–49 | New | Yellow badge, safety warning on install |
| 0–19 | Unreviewed | Red badge, strong warning + confirmation dialog |

### 6.3 Implementation

**New file:** `src/waves/community-trust.ts`

```typescript
export interface TrustFactors {
  scanPassed: boolean;
  highFindings: number;
  criticalFindings: number;
  sandboxPassed: boolean;
  reviewCount: number;
  averageRating: number;
  installCount: number;
  authorPublishedCount: number;
  daysSincePublish: number;
}

export type TrustTier = 'trusted' | 'community' | 'new' | 'unreviewed';

export function computeTrustScore(factors: TrustFactors): number;
export function getTrustTier(score: number): TrustTier;
```

Trust score is computed server-side when building WaveCards and stored in the
`wave_community_trust` table for caching.

## 10. Security Considerations

### 10.1 Publish-Time Security

| Check | Enforcement |
|-------|-------------|
| Security scan (critical findings) | **Hard block** — cannot publish |
| Security scan (high findings) | **Warning** — allowed but trust score penalized |
| Sandbox execution crash | **Hard block** — cannot publish |
| Sandbox timeout (>10s) | **Hard block** — cannot publish |
| Package size > 100KB | **Hard block** — prevents binary blobs |
| Reserved name prefix (`lil-dude-`) | **Hard block** — reserved for official |
| Duplicate name (existing in registry) | **Hard block** — use version bump instead |

### 10.2 CI-Time Security (wave-registry repo)

The GitHub Actions pipeline **re-runs the security scanner and sandbox** on the
submitted code. This prevents:
- Modified scan results (user could have patched their local scanner)
- Man-in-the-middle between local scan and PR creation
- Version skew between user's scanner and latest rules

### 10.3 Install-Time Security

The existing `installWave()` flow already runs:
1. Manifest validation (Zod schema)
2. Permission checking (against security level)
3. Git clone isolation (temp dir, `--depth 1`)

**New for community waves:**
4. Package hash verification (compare against registry's `packageHash`)
5. Trust tier logging (to `security_log` for audit)
6. Re-scan on install (optional, configurable via security level)

### 10.4 Supply Chain Protections

| Attack Vector | Mitigation |
|---------------|------------|
| Malicious code in index.js | Security scanner (41 patterns) + sandbox + CI re-scan |
| Typosquatting (similar names) | Naming rules + maintainer review on PR |
| Dependency confusion | Waves are self-contained (no npm deps); `dependencies` field is wave-to-wave only |
| Account takeover (GitHub) | Package hash verification; trust score decay if scan regresses |
| Backdoor in update | CI re-scans every version; hash changes tracked |

### 10.5 Privacy

- No user data sent to registry. Install counts are anonymous (incremented locally,
  not reported upstream).
- GitHub token is stored in local config file (`~/.lil-dude/config.json`), never in DB.
- Author profiles are opt-in (only created when publishing).

## 15. Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Low community adoption | Medium | Low | Seed with existing waves; Shorebreak-to-publish makes it frictionless |
| Malicious wave bypasses scanner | Low | High | CI re-scan; trust scoring; hash verification; security scanner is continuously improved |
| GitHub API rate limiting | Medium | Medium | Token-based auth (5000 req/hr); cache aggressively; degrade gracefully |
| Registry repo grows large | Low | Low | Git sparse checkout for install; wave packages are <100KB each |
| Maintainer bottleneck on PRs | Medium | Medium | Clear CONTRIBUTING.md; automated CI validation reduces review burden; consider auto-merge for trusted authors |

## 16. Future Considerations (Not in Scope)

These are explicitly deferred and should NOT be implemented in the initial sprints:

- **Wave versioning/rollback** — users can uninstall + reinstall; formal rollback is future work
- **Paid waves / monetization** — Lil Dude is open source; no payment infrastructure
- **Private registries** — enterprise feature, requires auth layer changes
- **Wave composition** — chaining waves as dependencies is v2 of this feature
- **Automatic trust score publishing** — upstream install counts to registry is a privacy concern; needs community discussion
- **Wave signing** — cryptographic signing of packages; worthy goal but adds significant complexity
